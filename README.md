# Dowe Pinless

> A Windows credential provider that replaces normal PIN-based sign-in with time-based one-time passwords (TOTP) and backup recovery codes.

## Overview

Dowe Pinless is a Windows sign-in credential provider intended to offer an alternative to the usual PIN workflow. Instead of entering a reusable PIN, a user authenticates with a short-lived TOTP code generated by a compatible authenticator application. When the authenticator is unavailable, a previously generated single-use backup recovery code can provide an emergency recovery path.

The project is currently under development. It is not ready for production use or deployment on systems where loss of access would be unacceptable.

## Implemented Proof of Concept

- Windows 10/11 V2 Credential Provider tile
- LocalSystem validation service with a versioned local named-pipe protocol
- RFC 6238 HMAC-SHA-1 TOTP with six digits, 30-second periods, and ±1-step tolerance
- CNG-generated 160-bit seeds protected by machine-scope DPAPI
- Persisted TOTP replay prevention
- Ten single-use recovery codes stored as salted SHA-256 hashes
- Constant-time comparison of TOTP digits and recovery-code hashes
- Per-account failed-attempt delay
- Enrollment and verification utility producing a standard `otpauth://` QR payload
- Explicit install/uninstall scripts that leave built-in Windows providers enabled

The POC validates Dowe Pinless codes but does not yet complete a TOTP-only Windows logon.
A Credential Provider gathers and serializes credentials; it is not an LSA authentication
authority and cannot turn a valid TOTP into a password, Windows Hello private key, or logon
token. See [`docs/Architecture.md`](docs/Architecture.md) for the boundary and later options.

## Security Notes

Credential providers operate in a security-sensitive part of Windows. Dowe Pinless should be treated as experimental until it has undergone careful threat modeling, code review, testing, and an independent security assessment.

The intended security design includes the following principles:

- TOTP secrets must never be stored in plaintext.
- Secret material should be protected with Windows security facilities such as DPAPI, CNG, TPM-backed keys, or an equivalently appropriate mechanism.
- Backup codes should be generated with a cryptographically secure random-number generator and stored only in a protected, non-recoverable representation when practical.
- Every backup code must be invalidated immediately after successful use.
- TOTP verification should use a deliberately small clock-skew window and reject replay of an accepted code within that window.
- Authentication codes, TOTP seeds, recovery codes, encryption keys, and other secrets must not appear in logs, crash reports, telemetry, or diagnostic output.
- Comparisons of sensitive values should use constant-time operations where applicable.
- Enrollment, reset, recovery-code generation, and administrative configuration require protections at least as strong as the sign-in flow itself.

TOTP does not automatically provide phishing resistance, and the security of the system depends on the enrollment process, local secret protection, recovery path, Windows configuration, and the security of the authenticator device.

## Requirements

The exact supported environment will be documented as implementation and testing progress. The expected development requirements are:

- A supported 64-bit version of Windows 10 or Windows 11
- Visual Studio with the Desktop development with C++ workload
- A compatible Windows SDK
- Administrator privileges for credential-provider registration and local testing
- A TOTP authenticator compatible with the project's final enrollment format
- A disposable virtual machine with snapshots for development and testing

> **Important:** Do not perform early credential-provider testing on your only Windows installation. A faulty provider or registration configuration can prevent sign-in. Keep another tested administrator account and an independent Windows sign-in method available.

## Installation

Use a disposable x64 Windows VM with a snapshot, a separate recovery administrator, and a
tested Windows password. Build first, then run the following from an elevated PowerShell session:

```powershell
.\installer\Install-DowePinless.ps1 -BuildDirectory .\x64\Release
& "$env:ProgramFiles\Dowe Pinless\DowePinlessEnroll.exe"
```

The installer registers the Dowe Pinless provider and validator service. It does **not**
register a provider filter or disable Windows password, PIN, Hello, or recovery providers.
See [`docs/Operations.md`](docs/Operations.md) before installing.

## Building from Source

Requirements are Visual Studio 18 with the Desktop development with C++ workload, the MSVC
v145 toolset, and a Windows 10/11 SDK. The source uses C++17 and has no package-manager
dependencies.

```text
1. Clone the repository.
2. Open DowePinless.sln in Visual Studio.
3. Select Release and x64.
4. Build the solution.
```

The build emits `DowePinlessCredentialProvider.dll`, `DowePinlessService.exe`, and
`DowePinlessEnroll.exe` under `x64\Release`.

## Usage

The current POC flow is:

1. Enroll using `DowePinlessEnroll.exe` and import its `otpauth://` payload.
2. Save the ten recovery codes offline.
3. Run `DowePinlessEnroll.exe --verify` with two consecutive TOTP values.
4. Select the **Dowe Pinless** tile and validate a current TOTP or unused recovery code.
5. Finish sign-in using a built-in Windows provider while this remains a validation POC.

Enrollment, account association, recovery, reset, and administrative usage instructions will be documented as those components become available.

## Backup Recovery Codes

Backup recovery codes are intended for emergency access when the enrolled authenticator cannot be used.

- Generate codes only from an authenticated, trusted enrollment or settings flow.
- Store them offline in a secure location, such as a protected password manager or a physically secured printed copy.
- Keep them separate from the computer they unlock whenever possible.
- Treat every code like a password: anyone who obtains an unused code may be able to sign in.
- Each code is intended for one-time use and should become invalid immediately after successful authentication.
- Regenerating a set should revoke every code from the previous set.
- Generate a replacement set promptly if any code may have been exposed or lost.

The final implementation will document code format, quantity, regeneration, revocation, storage protection, and administrative recovery behavior.

## Development Notes

- Develop and test inside a virtual machine with a working snapshot and recovery path.
- Preserve at least one independent Windows sign-in method throughout development.
- Keep core TOTP verification, replay protection, backup-code handling, and secure storage logic isolated and unit-testable.
- Test clock drift, expired and reused codes, malformed input, interrupted enrollment, corrupt state, account changes, upgrades, rollback, and uninstall behavior.
- Minimize code executing on the secure desktop and avoid unnecessary network dependencies in the sign-in path.
- Fail safely: an internal error must not silently authenticate a user or leave sensitive material exposed.
- Avoid disabling built-in credential providers until recovery behavior has been validated.
- Sign release binaries and publish reproducible verification guidance before distributing installable builds.

Contributions and security-reporting instructions will be added when the repository is ready for external collaboration. Until then, avoid publishing suspected vulnerabilities in a public issue.
